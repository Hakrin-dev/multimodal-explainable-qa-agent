## 3. 裁决（按 PLAN §10 规则）

准确率平手（差 0% < 5%）→ 按成本与延迟定：

1. **延迟**：DeepSeek P50 快 **34%**（2.2s vs 3.4s）——演示体验与端到端时延评分项直接受益
2. **成本**：名义单价 Qwen 更低，但 DeepSeek 前缀缓存已实测命中 89.1%
   （三层 Prompt 模板的第一层收益），两模型本负载成本差 <15%，量级相同
3. **可观测性**：DeepSeek 显式返回 `prompt_cache_hit_tokens`，
   §11.3 的成本工程叙事（缓存前后成本曲线）开箱即可量化

### ✅ 定案：主力 LLM = DeepSeek-V3（deepseek-chat）

- `.env`: `LLM_PROVIDER=deepseek`（已更新）
- 备胎保留配置项：`LLM_PROVIDER=qwen` 一键切换，不做自动 failover（D1 决议）
- **待补**：RAG 维度 5 用例（评测环境为 B 干净交接态，知识库待重摄入后补测；
  切换为纯配置操作，不影响 NL2SQL 结论的稳健性——两模型 RAG 生成侧共享同一检索上下文）

## 4. 附带发现（进 W2 迭代清单）

1. **同名曲目语义分歧（当前 3 个失败的共同根因）**：Chinook 存在不同专辑同名曲目；
   参考答案按曲名聚合（用户视角），模型按 trackid 聚合（物理视角）。裁决：用户视角为准，
   W2 将「同名曲目视为同一首」写入 schema 语义卡（半静态层）——正是“知识外置”架构的用武之地
2. **校验器子查询 clamp bug（已修）**：曾对派生表注入 LIMIT 50 导致 mt-018 平均值算错；
   已改为仅 clamp 最外层 + 回归测试（W1-D2 教训）
3. **确定性排序规则已入静态层**：并列名次边界曾导致 top-N 用例行集漂移；
   规则 4 追加「主排序键后必须追加次要排序键」
4. 修复循环全程未触发（60+31 次调用零校验/执行错误）→ sqlglot 校验 + schema 卡
   已经把无效 SQL 挡在执行前，W3 复杂多表用例再观察
5. 语义匹配器 4 级设计已沉淀（`run_nl2sql.py`），strict/semantic 双口径上报
