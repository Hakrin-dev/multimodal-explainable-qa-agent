## 2. 裁决（按 PLAN §10 规则）

评测过程分两阶段，恰好构成一次自然的消融：

- **初测（v0.2 模板）**：两模型平手 90%/90% → 按延迟与缓存可观测性倾向 DeepSeek
- **终测（v0.3 模板：clarify options 规则 + 同名曲目业务规则 + TOP-N 启发式 + 语义 4 级匹配器）**：
  差距拉开——**DeepSeek 双维度均领先 10+ 个百分点且延迟快 46%，主力定案不再依赖成本裁决**

### ✅ 主力：DeepSeek-V3（deepseek-chat）—— 双维度决定性胜出

- `.env`: `LLM_PROVIDER=deepseek`（已生效，容器健康检查可见）
- 备胎 `qwen` 保留配置项一键切换（RAG 侧仅差 1 个用例，作为备胎完全够用），不做自动 failover（D1）
- 前缀缓存实测：generate 侧命中率 **89.1%**（三层 Prompt 模板收益），成本工程叙事（§11.3）开箱可量化
- 成本量级：单轮全量评测 ≈ ¥0.5，预算消耗见 §5

## 3. 评测过程中发现并修复的问题（进 W2 迭代记录）

1. **LLM 响应缓存 key 漏 provider**：同模型名跨 provider 会共享缓存污染对比（选型探测时抓到，已修 + 回归测试）
2. **校验器子查询 clamp bug**：曾对派生表注入 LIMIT 50 导致统计语义被污染（mt-018 教训，已修 + 测试）
3. **TOP-N 并列行集漂移**：静态层追加确定性排序规则（模板 v0.2→v0.3 演进的一部分）
4. **同名曲目聚合语义**：业务规则入 PG 表注释（知识外置示范），模型按新规则修正行为
5. 语义匹配器 4 级设计（有序→无序→列名映射→含冗余列），strict/semantic 双口径上报
