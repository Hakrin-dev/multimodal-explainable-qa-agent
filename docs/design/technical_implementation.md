## 1. 系统总体架构设计

### 1.1 设计目标与约束

| 目标 | 量化要求 | 实现结果（终验） |
|---|---|---|
| 精准问数 | NL2SQL 执行准确率 ≥90% 得满分 | **100%（61/61）** |
| 忠实问答 | RAG 答案忠实度 ≥90% 得满分 | **100%**（含逐句引用自检） |
| 可解释 | SQL/检索片段/推理链路全展示 | Trace 树 + SSE 实时推送 + 回放 |
| 跨源融合 | 覆盖 ≥5 类跨源问题 | 5 类（db2doc/doc2db/doc2doc/dbdoc/clarify）11/11 |
| 鲁棒 | 错别字/别名/坏文档下稳定 | 30 变体全过 + 坏文档修复链路 |
| 效率 | 复杂度分析 + ≥3 规模实测 | 3 文档规模 × 2 表规模矩阵出图 |
| 成本 | API 预算 ≤¥1000 | 全周期实付 **¥4.19** |

工程约束：单机（WSL2 + RTX 5060 8GB）可完整复现；受限网络下全部依赖有镜像/备用通道；
无 API key 时 mock provider 可跑通全链路（评审友好）。

### 1.3 五个关键设计决策

1. **自研轻量编排内核（事件驱动）**：意图路由/工具调度/DAG 执行/Trace 全部可控，
   避免框架黑盒；单机部署零额外依赖。
2. **知识外置（检索式要素中台）**：业务别名、Schema 语义卡、公式、槽位矩阵全部沉淀为
   **数据库/配置文件资产**，Prompt 只含通用能力——新领域零改码接入（中级任务 #2 的核心）。
3. **校验优先**：SQL 必须过 sqlglot AST 校验 + 表白名单（Schema Linking 选择集）+
   只读执行；答案必须过逐句引用支撑自检。**错误拦截在展示之前**。
4. **全链路 Trace**：每个节点（intent/plan/tool_call/llm_call/fuse/clarify/step）产出统一事件，
   同时服务可解释性评分与调试效率；支持 PG 持久化与回放。
5. **成本工程**：三层缓存（提供商前缀缓存 / 应用层响应缓存 / 摄入增量缓存）+
   全量用量账本，实付 ¥4.19 完成全部研发与评测（详见 §7.5）。

### 1.4 技术栈与部署

后端 FastAPI + SQLAlchemy 风格手写 SQL（psycopg3）；pgvector 存向量；SQLite 存 LLM 账本；
前端 Vue 3 + TS + Vite + Naive UI + AntV X6（DAG）+ ECharts（图表）；
`deploy/docker-compose.yml`（pgvector + backend + frontend）+ `quick_start.sh` 一键启动
（含数据导入、术语抽取、知识库摄入与冒烟，幂等可重跑）。环境变量全部经 `.env` 注入，
密钥不入库；受限网络镜像源已参数化。

## 2. NL2SQL 模块技术实现 【A】

### 2.1 流水线总览

```
问题 ─①多轮改写(指代消解)─▶ ②术语标准化(三级匹配) ─▶ ③Schema Linking(召回+精排+列级)
    ─▶ ④Join 路径注入 ─▶ ⑤SQL 生成(先分析草稿后 SQL) ─▶ ⑥校验与自修复(≤3 轮)
    ─▶ ⑦执行(只读+行数/超时预算) ─▶ ⑧空结果归因 ─▶ ⑨结果解释+图表建议
```

每步均有 Trace 节点；下游全部使用改写后的**自包含问题**。

### 2.2 多轮改写与术语标准化（中级 #1/#2）

- **指代消解改写**：`agent.rewrite` 家族（冻结 Prompt），从会话历史补全指代/省略；
  规则 4 约定“多个同类要素只取最近轮次，严禁合并”；解析失败回退原问题。
  实测：`"那 2023 年呢"` → `"2023 年销售额是多少"`；改写对照进 Trace 与响应字段（前端展示）。
- **术语三级匹配**（`nl2sql/rewriter.py`）：
  1) **精确/最长匹配**：别名表（129 词条 / 717 别名，含人工审核的错别字变体如 摇磙→Rock）；
  2) **编辑距离**（脚本感知规则）：拉丁词 ≥4 字符且距离=1（Muzic→Music ✓、Jane→Jazz ✗）；
     中文词等长 ≥3 字且距离=1——根治了 2 字中文片段的灾难假阳性（歌有→Opera 类）；
  3) **pgvector 语义召回**（sim ≥0.8，span ≥3 中文字/4 拉丁字符）。
- **别名治理闭环**：LLM 批量生成 → 规则过滤（品类词黑名单、混合脚本、跨实体歧义按
  “基础词规则”归并）→ 人工抽检 → 入库；`gen_aliases.py` 固化全部规则，可安全再生成。
- **可扩展性（#2）**：新领域接入 = 跑一次抽取脚本 + 补种子别名文件 + （可选）LLM 生成别名，
  **Prompt 零改动**；表级业务规则以 PG 表注释承载（如 track 的同名曲目去重约定），
  自动进入 Schema 语义卡。

### 2.3 Schema Linking（中级 #4）

离线：每表生成**语义卡**（表名/中文注释/列/外键/样例值），关键词（jieba）+ 向量双索引。
在线：

```
问题 → 双路召回(关键词原始重叠计分 + 向量余弦) → RRF 融合 ∪ 双模态头部并集
     → FK 连通分量桥接(仅连接必需) → 相关性排序的伙伴扩展(上限 9 表)
     → LLM 精排(只删不加 + FK 连通性重桥 + 解析失败优雅降级) → 压缩 DDL + 列级标注
     → 显式 Join 路径(外键图生成树, 最高度起点) 注入 Prompt
```

| 指标 | 全 Schema 基线 | Linking v0 | **Linking v1（精排）** |
|---|---|---|---|
| L1 准确率 | 100% (31/31) | 100% | **100% (31/31)** |
| 平均表数 | 11 | 7.5 | **2.1** |
| Schema tokens | 1280 | ~900 (−30%) | **331（−74%）** |
| 71 表规模（合成实测） | — | — | 召回 3/3，P50 160ms |

干扰表排除（Invoice vs InvoiceLine 类）由 LLM 精排负责，规则为**只允许删除召回候选**，
不引入新表；删除后做 FK 连通性复检并桥接，防止“删过头”导致不可 JOIN。

### 2.4 Join 路径推理（中级 #5）

外键图（`pg_meta` 实时读取）→ 选中表诱导子图的**生成树 BFS**（最高度表为根）→
输出显式路径（如 `track.genreid = genre.genreid`）注入 Prompt 半静态层；
Prompt 静态层规则要求“关联必须使用给定路径”。多表用例（21 例，2–5 表 JOIN）
终验全过；自修复循环对 Join 错误可重试 ≤3 轮。

### 2.5 生成与校验

- **双步输出**：先【分析】（目标表/过滤/聚合/排序）再【SQL】，草稿直接进 Trace（可解释素材）。
- **sqlglot 校验**：单条语句、仅 SELECT、表存在性、**表白名单（Schema Linking 选择集）**、
  列存在性（qualify）、危险函数黑名单、LIMIT 截断（仅最外层，子查询不注入）。
- **启发式守卫**：问题含“前 N/TopN”但 SQL 无 LIMIT → 判为校验失败进入修复轮
  （含中文数字解析；“前一年”类时间表述不误报）。
- **执行**：只读连接 + statement_timeout + 行数预算；连接层带 5 次退避重试
  （针对 WSL2 docker-proxy 闪断）。

### 2.6 自修复与空结果归因

修复循环 ≤3 轮，回喂“校验错误/执行错误/表范围提示”，错误类型包括列名、语法、
白名单越界、限流提示。**空结果归因**（`empty_attr.py`）：执行返回 0 行时，
sqlglot 提取过滤字面量 → 在对应列上做 distinct 核对：
- 值存在但条件组合查不到 → `truly_no_data`（附 `count(*)` 佐证，如实回答）；
- 值不存在（疑似拼写/别名问题）→ `suspicious_filter` 并给出最近邻值修复建议；
- 语义空修复：`COUNT(*)` 空集返回一行 0 的语义被正确判为“空结果”而非 ok。

## 3. RAG 问答模块技术实现 【B】

### 3.1 摄入流水线（中级 #7/#8/#9 载体）

```
PDF ─①质量评估(#9)─▶ ②复杂度评分(#8)→解析路由 ─▶ ③解析(PyMuPDF/MinerU/PaddleOCR)
    ─④目录/层级重建(#7)─▶ ⑤层级感知切片(面包屑) ─▶ ⑥公式登记(#6) ─▶ ⑦混合索引+元数据
```

- **质量评估**：逐页检测 方向/倾斜/清晰度/文本层/繁体，输出 warnings 与总分；
  检测失败在写 embedding 之前终止（不污染索引）。
- **复杂度评分**：可解释规则加权（无文本层+3、表格页+1、页数/图片占比…）→ 1–5 级 →
  路由 PyMuPDF 直抽 / MinerU GPU / OCR 归一化；评分细节入 IR 元数据。
- **层级切片**：字号统计标题识别（文档标题 level0 + H1/H2 相对字号阈值），
  不跨 H1 切片、H2 起新 chunk、硬换行智能拼接（“5 天”不被拆断）；
  breadcrumb = 文档 > H1 > H2。
- **修复工作流（管理台后端）**：上传 → 质量报告 → 一键修复（方向校正/去模糊/OCR/繁简），
  实测清晰度 0.025 → 0.331（13x）；坏文档样本 3 份（旋转扫描/模糊繁体/目录丢失），
  目录丢失样本恢复文档标题 + 6 个 H1。
- **公式登记**：候选块筛选 → LLM 结构化抽取（`rag.ingest` 家族）→ 表达式与参数校验 →
  `kb_formula` 原子替换；默认开关关闭，失败/部分拒绝不覆盖已有有效公式。
  实测：候选 6 → 抽取 1（销售提成公式，latex 校验通过，rejected=0）。

### 3.2 混合检索与重排

- 稠密：pgvector 存块向量（本地 bge-small-zh 512 维；BGE-M3 1024 维版本已在
  GPU 环境验证：吞吐 ~1318 texts/s、与 reranker 同驻峰值 4.37GiB）；
  查询向量与库向量归一化后余弦计算。
- 稀疏：jieba 分词 + BM25（k1=1.5, b=0.75），内存索引。
- 融合：**RRF**（k=60，双路各取 top-20）→ 可选 **Cross-Encoder 精排**
  （bge-reranker-v2-m3，Top-20 rerank P50 ≈12ms）→ Top-k 送入生成。
- 查询改写（B-D4，`rag.query_rewrite` 家族）：受限历史融合 + 可选 HyDE；
  **HyDE 仅作用于稠密路**，BM25/reranker 使用检索改写词；一次调用、严格 JSON、
  失败回退原查询并记录 degraded。

### 3.3 引用生成与忠实度自检

生成 Prompt（`rag.generate` 冻结家族）要求“每个事实句带 [n] 引用、只用给定片段、
查不到就说未找到”。生成后进入 **逐句忠实度自检**（`rag.factcheck` 家族）：
仅依据检索片段判断每个事实是否有支撑；发现无支撑/错误引用 → 收敛重写（≤2 轮）；
非法 JSON/异常/空重写均优雅降级保留原答案；`initial_answer` 与最终答案双存，
Trace 记录轮次/重写/降级状态。真实对抗案例：错误事实（“15 天+500 元补贴”→10 天年假）、
错误引用（5%[1]→3%[2]）均被修复。

### 3.4 引用溯源

`citations[] = {doc, doc_id, page, breadcrumb, snippet, score}` 六字段契约；
前端点击引用经 `GET /api/docs/{id}/pdf?version=repaired` 打开对应版本 PDF 并定位页码——
契约明确 **页级定位**边界（不承诺页内矩形框选，需扩展须同步 IR/DB/契约/前端）。

## 4. 多源异构数据融合推理策略 【A】

### 4.1 意图路由与工具集

一次 LLM 结构化输出（`agent.intent` 家族，JSON 修复重试 + 关键词兜底）路由五类意图：
CHAT / DB_QUERY / DOC_QUERY / HYBRID / AMBIGUOUS。工具注册表：

| 工具 | 载体 |
|---|---|
| `nl2sql(question, history)` | NL2SQL 流水线（§2） |
| `rag_search(question)` | RAG 流水线（§3） |
| `formula_eval(question)` | 公式引擎（§4.3） |
| `db_lookup_entity(term)` | 术语库反查 |
| 澄清（ask_user 语义） | 槽位矩阵 + 会话挂起（§4.4） |

确定性拦截器补充 LLM 路由的波动：**公式关键词拦截**（提成/公式类 → formula_eval，
绕过 planner 不确定性）、**多文档对比拦截**（对比词+文档名词 → 强制 HYBRID 双路检索），
两者均产出 Trace 节点（`formula_intercept` / `multidoc_intercept`），可解释。

### 4.2 HYBRID 任务 DAG（真依赖编排）

规划器（`agent.plan` 家族）输出 `{id, tool, question, depends_on}` 任务图；
内核执行**拓扑波次**：入度 0 的子任务用线程池并发（≤3），依赖任务等待上游完成——
占位符 `{tN.result}` 注入上游结果（**紧凑实体 key 优先**，避免长摘要稀释下游检索质量）；
环依赖容错回退；全子任务完成后 `fuse`（`agent.fuse` 家族）做**分区溯源**生成
（[数据库]/[文档名+页码]）。实测：依赖链（冠军查询→档案检索）与并行双源
（摇滚vs爵士销量 ∥ 提成规定）均正确，并行场景端到端 4.6s。

### 4.3 公式计算引擎（跨源类型② Doc→DB）

FormulaIR 契约：`{latex, name, params{desc,unit,source}}`，`source ∈ {db,doc,user}` 决定绑定通道。
流程：公式匹配（关键词）→ **参数三通道绑定**（文档内数值 / 用户输入 / **数据库子查询**：
LLM 生成参数子问题 → 嵌套 nl2sql 工具调用 → 取 summary 底线数值防 count/sum 误读）
→ LaTeX→SymPy（受限 token 守卫）→ **双通道校验**（SymPy 符号求值与受限命名空间
Python 求值交叉验证，不一致则降级说明）→ 计算步骤进 Trace。
演示：`按员工手册提成公式 Jane 的提成` → S=833.04（DB）→ 0.03×833.04 = **24.9912**（steps=4）。

### 4.4 澄清机制（中#3）

**槽位矩阵外置配置**（`data/slot_matrix.json`）：按问题模式（增长率/对比/趋势）定义
必要槽位 + `satisfied_by` 证据正则 + 候选选项 + **同义词词表**。内核流程：
LLM 意图 → 矩阵校验（缺槽则**确定性覆写**为澄清；LLM 已判澄清则用矩阵**规范化槽位名**
并补强选项）→ 选项式澄清挂起（会话持久化，TTL 600s）→ 用户点选回填 → 改写器合成
自包含问题继续执行。**去历史重判**（standalone retry）：改写已自包含且矩阵零缺槽时，
去掉历史再判一次意图，治疗多轮简短输入的过度澄清。实测 30/30。

### 4.5 五类跨源问题与实测

| 类型 | 例 | 机制 |
|---|---|---|
| DB→Doc 实体档案 | 2024 冠军是谁+方法论 | DAG 依赖链 + 紧凑实体注入 |
| Doc→DB 参数查询 | 按手册提成公式算 Jane 提成 | 公式引擎三通道绑定 |
| Doc→Doc 多文档对比 | 年假制度 vs 投诉时限 | 多文档拦截 → 双 rag_search 并发 + fuse |
| DB+Doc 综合解释 | 销量最高曲风+运营说明 | DAG 并行 + 分区溯源 |
| 澄清后跨源续查 | 增长率（多轮） | 槽位矩阵 + 指代消解 + 会话 |

终验 **11/11 = 100%**（deepseek；qwen 9/11，路由层两模型均 100%——证明路由与模型无关，
生成质量与模型强相关）。

### 4.6 降级与诚实性

工具失败 → `degraded` 状态 + 明确原因（“知识库未就绪”“文档中未找到”），
绝不编造；跨源 fuse 对缺失子任务如实标注；空结果附 `count(*)` 佐证。
LLM 调用全部带超时/重试预算，DB 连接 5 次退避；单工具失败不拖垮整轮。

## 5. 可解释性实现方案

### 5.1 Trace 数据模型（契约 trace.md v0.2·冻结）

节点：`{id, parent_id, type, label, input, output, latency_ms, status, detail, started_at}`；
类型 8 种：`turn/intent/plan/tool_call/llm_call/fuse/clarify/step`；
状态 5 种：`ok/error/degraded/skipped/pending`。工具调用**嵌套**其流水线子树
（tool_call → rewrite/…/summarize），LLM 调用为孙节点并记 tokens/费用。
JSON Schema 权威定义 + 运行时一致性测试守护。

### 5.2 SSE 实时事件流（契约 §4.2）

```
turn.start{turn_id,…} → trace.node*(逐节点到达) / clarify.request → answer.delta*(逐token)
→ answer.done{完整 TurnResult} → turn.end{时延,成本} ；异常 → error{code,recoverable}
```

后端以“内核线程 + 队列”实时转发，前端凭 `answer.done` 做渲染锚点、
凭 `trace.node` 增量构建时间线/DAG；断线后可用 `GET /api/trace/{turn_id}` 拉全量树回放。

### 5.3 持久化与前端呈现

三表持久化：`trace_turn`（轮次摘要）/`trace_event`（扁平节点）/`app_session`（消息+挂起澄清），
均 best-effort 写入、跨重启恢复。前端：时间线（耗时/状态/输入输出）与
DAG（父子边+X6 分层布局）双视图；节点详情含 SQL/改写对照（before→after）/槽位校验/
命中引用列表；引用可跳 PDF 页码；数据卡片含 SQL 折叠、表格与图表建议。

### 5.4 成本可审计

每次 LLM 调用落账（provider/model/purpose/tokens/前缀缓存命中/费用/时延），
`GET /api/usage` 输出按 purpose 分解与缓存经济统计；单轮成本随 `turn.end` 返回——
“可解释”从推理扩展到成本维度。

## 7. 系统测试与性能评估

### 7.1 测试体系

- **分级评测** `eval/run_levels.py`：L0 smoke（每类 5 例，改 prompt 后跑）/

### 7.2 准确率终验（L2，30 runs，零基础设施失败、三重复零方差）

| Family（用例数） | DeepSeek（主力） | Qwen-Plus（备胎） |
|---|---|---|
| NL2SQL（61） | **100%**（首过 100%） | 83.6% |
| RAG 答案命中（41） | **100%**（检索 100%） | 93%（检索 100%） |
| 多轮（8 脚本 34 轮） | **8/8 · 34/34 轮** | 6/8 · 31/34 |

结论：路由/工具选择/计划结构**与模型无关**；生成质量与多轮保持**与模型强相关**——
据此 W1 选型定 DeepSeek 主力、Qwen 配置化备胎（一次环境变量切换，无代码改动）。

### 7.3 鲁棒性

错别字（Muzic→Music 等编辑距离修复）、别名/口语（巴西/帝都类）、混合脚本噪声
（生成期规则过滤）、坏文档 3 类（旋转/模糊繁体/目录丢失）、低质量输入下的**诚实降级**
（不编造）；30 个鲁棒性变体用例终验全过。

### 7.4 性能与伸缩性（实测矩阵，详见 `docs/milestones/w5_efficiency/`）

**文档规模（检索链路）**：

| 规模 | chunks | 检索 P50 | P95 | 标记召回@6 |
|---|---|---|---|---|
| 10 篇（真实） | 116 | 7.4ms | 9.1ms | — |
| 100 篇（合成） | 300 | 7.2ms | 9.1ms | 3/3 |
| 1000 篇（合成） | 3000 | 133.0ms | 150.4ms | 3/3 |

**表规模（Schema Linking）**：11 表 P50 55.2ms / 71 表 P50 160.4ms，召回均 3/3。

**复杂度与瓶颈**：向量路 O(N·d)（矩阵乘）；BM25 为内存 Python 实现 O(N·L)——
即 1000 篇时 133ms 的主因；优化路径 = pgvector HNSW + 数据库全文/外部索引
（决赛 Qdrant 分片），接口不变仅换实现。LLM 生成为端到端主导项（P50 ~2s/轮），
前缀缓存与 Schema 压缩持续压低其成本与首 token 时延。

### 7.5 成本工程（预算 ≤¥1000，实付 ¥4.19）
